# JWT Authentication Mechanism

**Date**: 2026-10-03

## 1. Changes Made
- `requirements.txt` & `pyproject.toml`: Added approved runtime dependencies `pyjwt>=2.8.0,<3.0.0` and `bcrypt>=4.0.0,<5.0.0`.
- `app/core/config.py`, `.env.example`, `.env`: Added JWT configuration settings (`JWT_SECRET_KEY`, `JWT_ALGORITHM`, `ACCESS_TOKEN_EXPIRE_MINUTES`).
- `app/core/security.py`: Implemented password hashing (`bcrypt`) and JWT access token encoding/decoding (`pyjwt`).
- `app/models/user.py` & `app/models/__init__.py`: Created SQLAlchemy `User` model with strict `Mapped[...]` typing and re-exported it.
- `alembic/env.py`: Added `import app.models` to ensure `target_metadata` registers all models for migrations.
- `alembic/versions/9afe86ec6c82_create_users_table.py`: Created migration revision for creating the `users` table with indexes on `id` and `email`.
- `app/schemas/auth.py` & `app/schemas/__init__.py`: Defined Pydantic models for `UserRegister`, `UserLogin`, `TokenResponse`, and `UserResponse`.
- `app/api/deps.py`: Implemented `get_current_user` FastAPI dependency using HTTP Bearer token validation and database lookup.
- `app/api/v1/endpoints/auth.py`: Implemented `/register`, `/login`, and `/me` routes adhering to session flush conventions (no manual `commit()`).
- `app/api/v1/router.py`: Mounted the auth router under `/api/v1/auth`.
- `AGENTS.md`: Added `pyjwt` and `bcrypt` to approved runtime dependencies list.

## 2. Why the Change Was Made (Rationale)
- The user requested a JWT authentication mechanism. Following the approved choice, a complete production-grade auth flow was implemented using standard `pyjwt` and `bcrypt` libraries.
- Decoupling password hashing and token generation into `app/core/security.py` allows reuse across CLI tasks, background workers, and endpoints.
- Authentication dependency `get_current_user` in `app/api/deps.py` provides a plug-and-play guard for future protected domain routes.

## 3. Things to Lookout for in Future Development
- **Production Secret Key**: Ensure `JWT_SECRET_KEY` in production environments is set to a cryptographically secure random string with at least 32 bytes (e.g. `openssl rand -hex 32`).
- **Database Migration Prerequisite**: When starting with a fresh database, run `alembic upgrade head` to apply the `users` table migration before testing registration or login.
- **Refresh Tokens & Revocation**: Currently, the system uses single access tokens. If session revocation or long-lived refresh tokens are required in the future, consider adding token blacklisting or refresh token rotation tables.
