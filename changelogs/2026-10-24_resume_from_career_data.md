# Resume Generation from Career Data with ATS-Safe PDF Export

**Date**: 2026-10-24

- `alembic/versions/1feee87e40de_create_resumes_table.py`: Added and applied the `resumes` migration with both foreign keys (`CASCADE` for user, `SET NULL` for job), indexes on `id`, `user_id`, and `job_id`, and the partial unique index.

- `app/services/resume.py`: Added `ResumeDraftService.build_draft`, a deterministic Markdown builder from the user profile, companies, experience logs, and skills. It filters `Role:` rows and orders experience and skills.
- `app/services/resume_export.py`: Added the strict Markdown-to-HTML renderer, WeasyPrint PDF export, pypdf-based verification returning `AtsReport` plus missing tokens, and `build_keyword_coverage`.
- `app/api/v1/endpoints/resumes.py`: Added authenticated CRUD, draft, PDF export, and ATS report endpoints with 404 ownership checks and 422/502 render error mapping.
- `app/api/v1/router.py`: Mounted the new router at `/api/v1/resumes`.
- `requirements.txt`: Added `weasyprint>=66,<71` and `pypdf>=6,<7`.
- `Dockerfile`: Added an apt install block for `libpangoft2-1.0-0`, `libpangocairo-1.0-0`, and `fonts-liberation`.

## 2. Why the Change Was Made (Rationale)
- The goal is a resume pipeline that generates Markdown from the user's already-stored career data, persists generated versions as historical records, optionally ties a version to a job posting, and exports a predictable PDF that ATS parsers can read.
- Resume markdown is stored per row instead of regenerated on every read so users keep a stable historical artifact even after they edit their companies, experience logs, or skills. There is deliberately no write-back into the companies, skills, or experience tables.
- Draft generation is deterministic string building rather than an LLM call, so the endpoint is fast, free, and reproducible, and it never invents summary text. The Summary section is omitted because there is no stored source for it.
- `Role: <title>` experience rows are auto-generated by the resume import workflow and were leaking into the experience section as bullet points. They are filtered out of the draft so an employer entry renders as company and dates only, which is more truthful to the underlying data model, which has no job-title column.
- The partial unique index enforces at most one canonical (untailored) resume per user at the database level while allowing any number of job-tailored resumes.
- PDF rendering uses a deliberately small Markdown subset. Unsupported constructs such as tables, images, raw HTML, code fences, nested lists, and multi-column markers raise a `ValueError` that becomes a 422 instead of silently producing a broken or technically unparseable document.

## 3. Things to Lookout for in Future Development
- The partial unique index `uq_resumes_user_job` allows only one resume per (user, job) pair. A second `POST /api/v1/resumes` for the same job returns 409; use `PATCH` to revise an existing resume instead. A second canonical (`job_id = null`) resume is also rejected with 409, but that rule is enforced in the API layer only, so two concurrent requests could theoretically both pass the pre-check.
- Deleting a job leaves its tailored resume row behind with `job_id = NULL`, preserving the submitted markdown as history. Those orphaned rows are indistinguishable from canonical resumes except by their stored `title`, so the frontend should label them as historical rather than treat them as the master resume.
- `Role: ...` experience logs are filtered out of generated drafts, so employers render without a job-title line until `CompanyWorked` gains a dedicated title column. Any future title support should update the draft serializer, not the filter.
- Docker now requires `libpangoft2-1.0-0`, `libpangocairo-1.0-0`, and `fonts-liberation` in the runtime image. Without them WeasyPrint either fails to import or silently substitutes a different font, so the PDF is no longer guaranteed to match the ATS-safe layout.
- PDF verification is heuristic: it checks heading presence, the first five words of each bullet, bold tokens, heading order, page count, and replacement characters in the extracted text. It does not validate visual layout, font embedding, or how a specific third-party ATS will parse the document.
- `-weasy-hyphens` is retained per the approved design but WeasyPrint 70 logs a deprecation warning for it; a future WeasyPrint upgrade may require removing the prefixed property.
- The new `weasyprint` and `pypdf` packages are listed in `requirements.txt` but `pyproject.toml` dependencies already lag behind the runtime list; keep them in sync if packaging from `pyproject.toml` becomes authoritative.
- WeasyPrint emits fontTools/HarfBuzz-subset warnings on hosts without `harfbuzz-subset`; these are non-fatal but can be silenced by installing that system package in the runtime image.
